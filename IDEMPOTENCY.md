# How idempotency works in this system

A map of the implementation: what each piece does, where it lives, and why it
is shaped that way. Line numbers are as of commit `deb64b3`.

---

## The problem

A client sends `POST /v1/transfers` and the response never arrives — a timeout,
a dropped connection, a killed process. The client cannot tell which of these
happened:

```
the request never arrived                    → the payment did NOT happen
the request arrived, worked, reply was lost  → the payment DID happen
```

Both look identical from the client's side: silence. Its only option is to
retry, and without idempotency the retry creates a second payment.

Reproduced by hand against the running API, with a deliberate delay after the
commit so the work lands and the acknowledgement is lost:

```
curl --max-time 1 POST /v1/transfers   → curl exit code 28, no response
GET  /v1/accounts/{source}             → balance -50000   (it worked)
POST /v1/transfers  (the retry)        → a second transfer
GET  /v1/accounts/{source}             → balance -100000  ← $500 paid twice
```

**The server cannot solve this alone.** A retry and a genuine second payment are
byte-for-byte identical; the difference exists only in the client's knowledge
that it is sending the same instruction again. So the client sends a key that
carries that knowledge.

---

## The contract

```http
POST /v1/transfers
Authorization: Bearer pk_live_...
Idempotency-Key: invoice-4471

{"source_account":"acc_...","destination_account":"acc_...","amount":50000,"currency":"USD"}
```

| | |
|---|---|
| Generated by | the client, once per payment |
| Reused on | every retry of that same payment |
| Never reused for | a different payment |
| Required | yes — `400` without it |
| Max length | 255 characters |

The key is generated **before the first attempt** and held constant across
retries. Generating it inside the retry loop defeats the whole mechanism: each
attempt would carry a different key and the server would see separate
instructions.

## 1. The schema

`db/migrations/000007_transfers_idempotency_unique.up.sql`

```sql
CREATE UNIQUE INDEX transfers_idempotency_key_idx
    ON transfers (idempotency_key)
    WHERE idempotency_key IS NOT NULL;

ALTER TABLE transfers ADD COLUMN request_fingerprint text;
```

**This index is the entire fix.** Not as a validation rule — as a concurrency
primitive.

When two transactions insert the same key:

```
A:  INSERT key ──── work ──── COMMIT
                                 │
B:  INSERT key ──[ BLOCKED ]─────┴──► fails with SQLSTATE 23505
         │
         └── B is stopped here, not slow. It cannot know whether A will
             commit or roll back, so it waits until A decides.
```

That blocking **is** the serialisation. Application code cannot produce it: a
mutex lives in one process's memory, and the two requests may be on different
machines. The database is the only thing both talk to.

Demonstrated in `idempotency_test.go:402`, which holds the key in an
uncommitted transaction and watches a second request block on it:

```
the second request is blocked on the held index entry: the unique index is
serialising the two writers, which no mutex could do across processes
```

**Why partial** (`WHERE idempotency_key IS NOT NULL`): the column is nullable,
because transfers created by something other than a client instruction — a
reversal in phase 4 — have no key. NULLs never collide with each other in SQL
anyway, so the predicate is not strictly required; it keeps the index free of
those rows and states the rule in the schema where a reader will see it.

## 2. Reading the header

`internal/api/transfers.go:312` — `idempotencyKeyFrom`

```go
func idempotencyKeyFrom(r *http.Request) (key, message string, ok bool) {
	key = strings.TrimSpace(r.Header.Get("Idempotency-Key"))

	switch {
	case key == "":
		return "", "Idempotency-Key header is required: ...", false
	case len(key) > maxIdempotencyKeyLength:   // 255, line 32
		return "", fmt.Sprintf("...at most %d characters, got %d", ...), false
	}
	return key, "", true
}
```

Called first thing in the handler, `transfers.go:96`, before the body is even
decoded.

**Required, not optional.** An optional key is forgotten exactly when it matters,
and the cost of forgetting is a duplicate payment. Stripe makes it optional for
backward compatibility with clients that predate the feature; this API has no
such history.

## 3. The four outcomes

`internal/api/transfers.go:155` — `createTransfer`

```go
func (s *Server) createTransfer(ctx, req, apiKeyID, idempotencyKey) (Transfer, int, error) {
	fingerprint := fingerprintRequest(apiKeyID, req)

	transfer, err := s.insertTransfer(ctx, req, apiKeyID, idempotencyKey, fingerprint)
	if err == nil {
		return transfer, http.StatusAccepted, nil          // ① first request
	}
	if !errors.Is(err, transfers.ErrDuplicateKey) {
		return transfers.Transfer{}, http.StatusInternalServerError, err
	}
	return s.replayTransfer(ctx, idempotencyKey, fingerprint)   // ② ③ ④
}
```

**The insert comes first.** No lookup before it. That order is the fix: reading
first and inserting if nothing came back leaves a window every concurrent
request passes through — measured at 99 transfers from 100 requests.

```
                    INSERT
                      │
       ┌──────────────┴──────────────┐
   succeeded                     23505
       │                             │
   ① do the work                 replayTransfer
      202 NEW                        │
                    ┌────────────────┼────────────────┐
              fingerprint       fingerprint      row not yet
                matches           differs          visible
                    │                │                │
              ② replay          ③ 422            ④ 409
                202 SAME      key reused      still in flight
```

---

### ① First request — `insertTransfer`, `transfers.go:189`

One database transaction containing everything:

```go
tx, err := s.db.Begin(ctx)
defer tx.Rollback(ctx)

    transfers.Insert(...)        // with idempotency_key and fingerprint
    ledger.Record(ctx, tx, ...)  // source debit → settlement credit
    transfers.SetLedgerTxn(...)

tx.Commit(ctx)
```

A transfer row without its ledger entries is an instruction nobody recorded;
entries without their transfer are money moved for no stated reason. Neither is
a state the system may be observed in, so both land or neither does.

Returns `202`, not `201`: the instruction is accepted, the money has not moved.

---

### ② A genuine retry — replay

`internal/api/transfers.go:238` — `replayTransfer`

The fingerprint matches, so this is the same instruction arriving again. Return
the **original transfer, with the same id, and the same `202`** — as though the
first response had not been lost.

**Not a 409.** The client retried because it did not know the outcome; telling it
"conflict" leaves it exactly as ignorant, and its only safe move would be to
retry harder.

Verified by hand — five retries with one key:

```
attempt: tr_40f8401f70148a6cf23d2dd424ddf09d processing
attempt: tr_40f8401f70148a6cf23d2dd424ddf09d processing
attempt: tr_40f8401f70148a6cf23d2dd424ddf09d processing
attempt: tr_40f8401f70148a6cf23d2dd424ddf09d processing
attempt: tr_40f8401f70148a6cf23d2dd424ddf09d processing

source balance: -50000    ← paid once
```

### ③ Same key, different request — `422`

`transfers.go:253`, inside `replayTransfer`:

```go
if existing.RequestFingerprint == nil || *existing.RequestFingerprint != fingerprint {
	return transfers.Transfer{}, http.StatusUnprocessableEntity, nil
}
```

The fingerprint is a SHA-256 of what was asked for — `transfers.go:295`:

```go
func fingerprintRequest(apiKeyID string, req createTransferRequest) string {
	sum := sha256.Sum256([]byte(strings.Join([]string{
		apiKeyID,                                  // scoped to the caller
		req.SourceAccount,
		req.DestinationAccount,
		strconv.FormatInt(req.Amount, 10),
		req.Currency,
	}, "|")))
	return hex.EncodeToString(sum[:])
}
```

**Why this matters more than it looks.** Without the check, a client that reuses
a key for a different payment gets the *old* transfer back with a `202`. Watched
failing with the check removed:

```
status = 202, want 422: the client asked for 80000 and received
{"amount":50000,...} — believing the larger payment succeeded
```

They think they paid $800. They paid $500. **They will never find out.**

**Why the api key is in the hash:** two callers must not collide on each other's
keys, and one must not be able to read another's transfer by guessing one.
Covered by `idempotency_test.go:319`.

---

### ④ Key taken, row not yet visible — `409`

`internal/api/transfers.go:266` — `awaitTransfer`

The duplicate error can arrive *before* the winning transaction commits: the
index entry is taken while the row is still invisible to everyone else. Looking
it up returns nothing, which does not mean it does not exist.

```go
const attempts = 10
const gap = 20 * time.Millisecond

for i := 0; i < attempts; i++ {
	transfer, err = transfers.FindByIdempotencyKey(ctx, s.db, idempotencyKey)
	if err == nil {
		return transfer, nil
	}
	...wait 20ms...
}
```

Retrying gives the winner a moment to finish, which turns most of these into a
correct replay. If it still has not committed after 200ms, return `409` with
`idempotency_key_in_flight`: nothing true can be said about the outcome yet, so
say exactly that.

PROGRESS.md §3.2 calls this *"where most implementations quietly break"* — they
return "transfer not found", or worse, create a second one.

## 4. Detecting the duplicate

`internal/transfers/transfer.go:101`

```go
func IsDuplicateKey(err error) bool {
	var pgErr *pgconn.PgError
	return errors.As(err, &pgErr) && pgErr.Code == pgerrcode.UniqueViolation
}
```

**Branches on SQLSTATE `23505`, not on the message text.** The message is
localised and changes between Postgres versions; a `strings.Contains` check
would silently stop matching on a German-locale server or after an upgrade —
and here, failing to detect the duplicate means creating duplicate payments.

`errors.As` rather than `==` because the error is wrapped with `%w` on the way
up, so the `*pgconn.PgError` is nested inside.

| 176 | `TestTransferRequiresAnIdempotencyKey` | missing, blank or oversized → 400, nothing written |
| 213 | `TestDifferentKeysCreateDifferentTransfers` | two genuine payments both go through |
| 241 | `TestSameKeyDifferentBodyIsRejected` | 422, original untouched |
| 294 | `TestSameKeyDifferentDestinationIsRejected` | a changed vendor is a changed request |
| 319 | `TestIdempotencyKeysAreScopedToTheCaller` | one caller cannot read another's transfer |
| 358 | `TestReplayDoesNotMoveMoneyAgain` | 5 requests → 2 ledger entries, not 10 |
| 402 | `TestKeyTakenButNotYetCommittedIsSerialised` | the second writer blocks, then replays |

Run them:

```bash
go test ./internal/api/ -run "Idempoten|SameKey|Replay|KeyTaken|Sequential|DifferentKeys" -v
go test ./internal/api/ -run TestIdempotentRequestsCreateOneTransfer -count=10 -race
```

**Two things worth knowing about the ⭐ test.**

It counts **rows in the database**, not `202` responses. All 100 responses were
legitimate `202`s even when the implementation was broken — every caller thought
it worked. The damage is in the table.

`-race` reports **nothing**, correctly. This is a race between two SQL
statements, not between two goroutines, so no Go tooling can see it. Only a test
that counts rows catches it.

## The shape, seen twice now

```
Phase 2, rate limiter    SELECT count → decide → UPDATE    50 of 50 allowed against a limit of 30
Phase 3, idempotency     SELECT key   → decide → INSERT    99 transfers instead of 1
```

Read, decide, write — with a gap. Same fix both times: a database constraint
that makes the second writer block and then fail, rather than succeed.

## Known limits

**The fingerprint is strict.** The same caller genuinely cannot reuse a key for a
different request — correct, but stricter than Stripe, which scopes keys per
account and expires them after 24 hours.

**Keys are kept forever.** There is no expiry, so `transfers` carries every key
ever used. Stripe expires them at 24 hours. Adding expiry here means deciding
what a replay of an expired key should do, which is a real design question, not
a cleanup task.

**`awaitTransfer` waits up to 200ms** on a request whose winner is slow. Under
heavy contention that occupies a connection. The alternative — failing
immediately with 409 — pushes the retry back to the client, which is worse for
the common case.
